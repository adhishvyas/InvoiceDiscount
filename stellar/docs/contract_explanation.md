# How the InvoiceDiscount Smart Contract Works

*A plain-English walkthrough for developers who are new to Soroban and Rust.*

---

## What problem does this contract solve?

Imagine a supplier (the **seller**) who has issued an invoice to a customer (the **buyer**) for $100,000, due in 60 days. The seller needs cash today — waiting 60 days is painful. The buyer, on the other hand, holds cash and could pay early, but only if there's something in it for them.

**Invoice discounting** is the deal: the buyer pays early and gets a discount. Pay in the first 15 days and only owe $85,000. Pay in days 15–30 and owe $90,000. Wait until the due date and pay the full $100,000.

This contract enforces that deal on the Stellar blockchain. No middleman, no trust required — the rules are in the code.

---

## A quick primer on the tech stack

- **Stellar** is a blockchain network built for financial applications (payments, tokenized assets, etc.).
- **Soroban** is Stellar's smart contract platform. You write contracts in Rust, and they run on-chain.
- **Rust** is a systems programming language known for safety and speed. You don't need to know it deeply — this post explains any Rust-specific concepts as they come up.
- A **token** on Soroban is just a smart contract that keeps a ledger of who owns how much of some asset (like USDC). The `token::Client` in this code is a standard way to interact with any such token.

## The file at a glance

Everything lives in a single file: `contracts/invoice_discount/src/lib.rs`. It is split into four sections:

## Section 1 — Storage keys

```rust
#![no_std]

use soroban_sdk::{
    contract, contractimpl, contracttype, symbol_short, token, Address, Env, Vec,
};

#[contracttype]
enum DataKey {
    Seller,
    Buyer,
    Token,
    Principal,
    DueDate,
    Tiers,
    Status,
}
```

**`#![no_std]`** — Soroban contracts run in a sandboxed environment that doesn't have access to Rust's full standard library (no filesystem, no threads, no OS). This line opts out of the standard library upfront.

**`use soroban_sdk::...`** — This imports the tools provided by the Soroban SDK: things like `Address` (a blockchain wallet address), `Env` (the gateway to all on-chain operations), and `Vec` (a list type).

**`DataKey`** is an *enum* — a type that can be exactly one of a fixed set of named values. Think of it as a set of named slots in a key-value store. On Soroban, contract data is stored as key/value pairs, and `DataKey` provides strongly-typed labels for each piece of data this contract needs to persist. `#[contracttype]` tells the Soroban compiler how to serialize these for on-chain storage.

## Section 2 — Data structures

### The discount tiers

```rust
#[contracttype]
#[derive(Clone)]
pub struct DiscountTier {
    pub cutoff: u64,
    pub discount_bps: u32, // e.g. 1500 = 15%
}
```

A **struct** in Rust is like a named object with fixed fields — similar to a TypeScript interface or a Python dataclass.

- `cutoff` — a Unix timestamp (seconds since 1 Jan 1970). If payment is triggered *before* this moment, this tier's discount applies.
- `discount_bps` — the discount expressed in *basis points*. One basis point is 0.01%, so 1500 bps = 15%. Using integers avoids floating-point rounding issues on-chain.

**`#[derive(Clone)]`** is a Rust macro that automatically generates the ability to make a copy of a `DiscountTier` value. Without it you can't duplicate the value, which the contract needs to do when reading tiers out of storage.

### The invoice lifecycle

```rust
#[contracttype]
#[derive(Clone, PartialEq, Debug)]
pub enum Status {
    Active,    // created, not yet funded
    Funded,    // buyer has locked principal
    Paid,
    Cancelled,
}
```

`Status` is an enum that tracks where the invoice is in its lifecycle. An invoice starts `Active`, moves to `Funded` when the buyer deposits money into the contract, then settles as `Paid` or `Cancelled`.

`PartialEq` lets us compare two `Status` values with `==`. `Debug` allows the value to be printed in error messages. Both are auto-generated by the `#[derive(...)]` macro.

### The full invoice snapshot

```rust
#[contracttype]
pub struct InvoiceState {
    pub seller: Address,
    pub buyer: Address,
    pub token: Address,
    pub principal: i128,
    pub due_date: u64,
    pub tiers: Vec<DiscountTier>,
    pub status: Status,
}
```

`InvoiceState` bundles all invoice data into one struct so the frontend can fetch everything in a single call. `i128` is a 128-bit signed integer — Soroban uses it for token amounts to avoid overflow with large numbers. `Address` is a Soroban type representing any account or contract on Stellar.

### `initialize` — setting up the invoice

```rust
pub fn initialize(
    env: Env,
    seller: Address,
    buyer: Address,
    token: Address,
    principal: i128,
    due_date: u64,
    tiers: Vec<DiscountTier>,
) {
    if env.storage().instance().has(&DataKey::Status) {
        panic!("already initialized");
    }

    seller.require_auth();

    assert!(principal > 0, "principal must be positive");
    assert!(due_date > env.ledger().timestamp(), "due date must be in the future");
    assert!(tiers.len() <= 10, "too many tiers");

    let mut prev_cutoff: u64 = 0;
    for i in 0..tiers.len() {
        let tier = tiers.get(i).unwrap();
        assert!(tier.cutoff > prev_cutoff, "tiers must be ordered ascending");
        assert!(tier.cutoff <= due_date, "tier cutoff must not exceed due date");
        assert!(tier.discount_bps <= 10_000, "discount cannot exceed 100%");
        prev_cutoff = tier.cutoff;
    }

    env.storage().instance().set(&DataKey::Seller, &seller);
    // ...stores all fields...
    env.storage().instance().set(&DataKey::Status, &Status::Active);

    env.storage().instance().extend_ttl(100_000, 100_000);
}
```

The seller calls this once to configure the invoice. A few things worth unpacking:

**`panic!`** is Rust's way of aborting with an error message. In Soroban, a panic rolls back the entire transaction — nothing is saved. It's the on-chain equivalent of throwing an exception that cancels all side effects.

**`seller.require_auth()`** — Soroban's authentication primitive. It verifies that the transaction was signed by `seller`'s private key before proceeding. Without this anyone could create invoices pretending to be someone else.

**`assert!(condition, message)`** — if the condition is false, the call panics with the message. Used here to enforce business rules: positive principal, future due date, no more than 10 tiers, tiers sorted in ascending order, no discount above 100%.

**`env.ledger().timestamp()`** returns the current block timestamp — the on-chain clock.

The `for i in 0..tiers.len()` loop walks each tier and checks it is valid. `tiers.get(i).unwrap()` retrieves the item at position `i`. In Rust, many operations return an `Option` (either `Some(value)` or `None`). `.unwrap()` extracts the inner value and panics if it's `None` — safe here because `i` is always within bounds.

**`extend_ttl(100_000, 100_000)`** keeps the contract's storage alive for at least 100,000 ledgers (roughly 139 days). On Soroban, data that isn't periodically "refreshed" expires to save network resources.

### `fund` — the buyer locks in their money

```rust
pub fn fund(env: Env) {
    let buyer: Address = env.storage().instance().get(&DataKey::Buyer).unwrap();
    buyer.require_auth();

    let status: Status = env.storage().instance().get(&DataKey::Status).unwrap();
    assert!(status == Status::Active, "invoice must be Active to fund");

    let token: Address = env.storage().instance().get(&DataKey::Token).unwrap();
    let principal: i128 = env.storage().instance().get(&DataKey::Principal).unwrap();

    token::Client::new(&env, &token)
        .transfer(&buyer, &env.current_contract_address(), &principal);

    env.storage().instance().set(&DataKey::Status, &Status::Funded);
    env.storage().instance().extend_ttl(100_000, 100_000);
}
```

The buyer calls `fund` to transfer the full invoice amount into the contract itself. The contract holds the money in escrow — neither party can touch it until `trigger_payment` or `cancel` is called.

`token::Client::new(&env, &token).transfer(...)` is a cross-contract call: this contract instructs the token contract to move `principal` tokens from the buyer's account to the contract's own address (`env.current_contract_address()`).

After the transfer succeeds, the status flips to `Funded`.

---

### `trigger_payment` — settling the invoice

```rust
pub fn trigger_payment(env: Env, caller: Address) {
    caller.require_auth();

    let seller: Address = env.storage().instance().get(&DataKey::Seller).unwrap();
    let buyer: Address = env.storage().instance().get(&DataKey::Buyer).unwrap();
    assert!(caller == seller || caller == buyer, "caller must be seller or buyer");

    let status: Status = env.storage().instance().get(&DataKey::Status).unwrap();
    assert!(status == Status::Funded, "invoice must be Funded");

    let now = env.ledger().timestamp();
    let tiers: Vec<DiscountTier> = env.storage().instance().get(&DataKey::Tiers).unwrap();
    let principal: i128 = env.storage().instance().get(&DataKey::Principal).unwrap();
    let token: Address = env.storage().instance().get(&DataKey::Token).unwrap();

    let discount_bps = Self::active_discount(&tiers, now);
    let discount_amount = principal * discount_bps as i128 / 10_000;
    let payment_to_seller = principal - discount_amount;
    let refund_to_buyer = discount_amount;

    let token_client = token::Client::new(&env, &token);
    let contract_addr = env.current_contract_address();

    token_client.transfer(&contract_addr, &seller, &payment_to_seller);
    if refund_to_buyer > 0 {
        token_client.transfer(&contract_addr, &buyer, &refund_to_buyer);
    }

    env.storage().instance().set(&DataKey::Status, &Status::Paid);

    env.events().publish(
        (symbol_short!("paid"), caller),
        (payment_to_seller, refund_to_buyer, discount_bps),
    );
}
```

Either party can trigger payment once the invoice is funded. The contract:

1. Checks which discount tier is currently active by calling the private `active_discount` helper.
2. Calculates how much the seller receives and how much is refunded to the buyer.
3. Executes both transfers atomically — either both happen or neither does.
4. Emits an on-chain event with the settlement details.

`discount_bps as i128` is a Rust *cast* — `discount_bps` is a `u32` (32-bit unsigned integer) and `principal` is an `i128`, so they need to be the same type before multiplication. `as i128` converts it.

`env.events().publish(...)` writes a structured log entry to the blockchain. Anyone watching the chain (a frontend, an indexer) can listen for `"paid"` events to react to settlements in real time.

### `cancel` — tearing it up

```rust
pub fn cancel(env: Env, caller: Address) {
    caller.require_auth();

    let seller: Address = env.storage().instance().get(&DataKey::Seller).unwrap();
    let buyer: Address = env.storage().instance().get(&DataKey::Buyer).unwrap();

    let now = env.ledger().timestamp();
    let due_date: u64 = env.storage().instance().get(&DataKey::DueDate).unwrap();
    let status: Status = env.storage().instance().get(&DataKey::Status).unwrap();

    let caller_is_seller = caller == seller;
    let caller_is_buyer_after_due = caller == buyer && now > due_date;
    assert!(
        caller_is_seller || caller_is_buyer_after_due,
        "not authorized to cancel"
    );

    assert!(
        status == Status::Active || status == Status::Funded,
        "cannot cancel a completed invoice"
    );

    if status == Status::Funded {
        let token: Address = env.storage().instance().get(&DataKey::Token).unwrap();
        let principal: i128 = env.storage().instance().get(&DataKey::Principal).unwrap();
        token::Client::new(&env, &token)
            .transfer(&env.current_contract_address(), &buyer, &principal);
    }

    env.storage().instance().set(&DataKey::Status, &Status::Cancelled);
}
```

Cancellation rules are asymmetric by design:
- The **seller** can cancel at any time before the invoice is paid.
- The **buyer** can only cancel *after* the due date has passed — this protects the seller from a buyer who funds and then immediately tries to cancel to get their money back without paying.

If funds were already locked, they are returned to the buyer in full before the status is set to `Cancelled`.

### `get_invoice` — reading the state

```rust
pub fn get_invoice(env: Env) -> InvoiceState {
    InvoiceState {
        seller: env.storage().instance().get(&DataKey::Seller).unwrap(),
        buyer: env.storage().instance().get(&DataKey::Buyer).unwrap(),
        token: env.storage().instance().get(&DataKey::Token).unwrap(),
        principal: env.storage().instance().get(&DataKey::Principal).unwrap(),
        due_date: env.storage().instance().get(&DataKey::DueDate).unwrap(),
        tiers: env.storage().instance().get(&DataKey::Tiers).unwrap(),
        status: env.storage().instance().get(&DataKey::Status).unwrap(),
    }
}
```

A pure read — no auth required, no state changes. The frontend calls this to display the invoice details. In Rust, the last expression in a function without a semicolon is automatically the return value, so there's no `return` keyword needed here.

### `active_discount` — the discount engine

```rust
fn active_discount(tiers: &Vec<DiscountTier>, now: u64) -> u32 {
    for i in 0..tiers.len() {
        let tier = tiers.get(i).unwrap();
        if now < tier.cutoff {
            return tier.discount_bps;
        }
    }
    0
}
```

This private helper (note: no `pub`) walks through the tiers in order. Since tiers are stored sorted by cutoff ascending, the first tier whose cutoff is still in the future is the one that applies. If no tier qualifies (the due date has passed), it returns `0` — full payment, no discount.

`&Vec<DiscountTier>` — the `&` means this function borrows the list rather than taking ownership of it. Rust's ownership model ensures memory safety without a garbage collector: every value has exactly one owner, but others can temporarily borrow it. Using `&` here means `active_discount` can read the tiers without consuming them.

## How a real deal plays out

1. Seller and buyer agree off-chain: $100,000 due in 60 days, with three discount windows.
2. **Seller calls `initialize`** with those terms. Status: `Active`.
3. **Buyer calls `fund`**. $100,000 moves from the buyer's wallet into the contract. Status: `Funded`.
4. **Time passes.** If the buyer triggered payment on day 5 (within the 15-day window): seller gets $85,000, buyer gets $15,000 back.  
   If payment is triggered on day 45 (past all discount windows): seller gets the full $100,000.
5. Status becomes `Paid`. Done.

## What the tests verify

The test module at the bottom of the file uses Soroban's local testing environment — a simulated blockchain that runs entirely in memory, no network needed.

| Test | What it checks |
|---|---|
| `test_full_payment_at_due_date` | After the due date, seller receives 100% of principal |
| `test_early_payment_first_tier` | In the first discount window, seller gets 85% and buyer is refunded 15% |
| `test_cancel_before_fund_refunds_nothing` | Cancelling before funding doesn't move any tokens |
| `test_cancel_after_fund_refunds_buyer` | Cancelling after funding returns the full principal to the buyer |
| `test_get_invoice_returns_state` | `get_invoice` returns the correct values after initialization |

`env.ledger().with_mut(|l| l.timestamp = ...)` lets tests fast-forward the on-chain clock to simulate time passing — no waiting required.

## Key takeaways

- The contract is a **trustless escrow**. Once funded, neither party can move money arbitrarily — only the settlement rules written in code can.
- **Discount tiers** give buyers a financial incentive to pay early, which is the entire point of invoice discounting.
- **All state lives on-chain** in Soroban's key-value store. The contract has no database, no server — just code and storage.
- **Auth checks protect every state-changing function** so no one can act on behalf of another party without their cryptographic signature.
