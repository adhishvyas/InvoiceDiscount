## Summary of what changes the plan

1. **Real TIP-20 works in plain local `forge test`.** The Tempo build runs the precompiles locally (template `network = "tempo"`). A test can create a real token with `StdPrecompiles.TIP20_FACTORY.createToken(...)`, grant itself `ISSUER_ROLE` and `mint`. AlphaUSD (`0x20c…0001`) also exists locally. No fork is needed for real memo events, and `MockTIP20` is no longer necessary for the unit suite. Fork tests are still useful for OUSD and the live token set. *(Plan decision "mock + fork" should be revisited, see §S2 below.)*
2. **`isTIP20` exists on the TIP-20 Factory precompile and checks code, not just prefix.** The spec's prefix-only check lets through unused prefixed addresses.
3. **`deal` does not work on TIP-20 balances**, but `vm.prank(holder)` plus `transfer` does.
4. **The `npm` on this machine is the Windows one** and fails on WSL paths. Use `corepack pnpm@9` (works) or install a Linux Node/npm.

| # | Item | Result | Detail |
|---|---|---|---|
| M0 | `mppx` API names | **confirmed** *(probed)* | Server: `Mppx.create({ methods, secretKey })`, `mppx.charge({ amount, currency, recipient, expires, description })(request)` → `{ status: 402, challenge: Response }` or `{ status: 200, withReceipt(response) }`. `amount` is in **display units** (`'85'` → `85000000` on the wire); `decimals` defaults to 6. `Expires.minutes(n)`. The 402 body is `application/problem+json`. `realm` defaults to the request hostname. Shared: `Challenge.fromResponse` / `fromHeaders` / `fromResponseList`, `Challenge.verify(ch, { secretKey })`, `Credential.fromRequest` / `serialize`, `Receipt.fromResponse` → `{ method, reference, status: 'success', timestamp, externalId? }`. Client: `Mppx.create({ methods: [tempo.charge(...)], polyfill: false }).fetch`. |
| M0b | `tempo.charge()` offers | **new** *(probed)* | `tempo.charge` returns a list of **offers**. With no `currency` it makes two (OUSD first, then the network fallback), so the 402 carries two `Payment` challenges that, with a per-call `currency`, are identical apart from `id`. Configuring a `currency` at create time gives one offer; the per-call `currency` still overrides it (probed with BetaUSD). |
| 1 | Wallet signing account for `mppx` | **confirmed** *(source)* | The Accounts SDK provider behind `tempoWallet` has `getMppxParameters()` → `{ getClient, resolveAccount }`. `getClient` returns a viem client whose account is the active Tempo Wallet address as a `json-rpc` account. Get it with `(await connector.getProvider()).getMppxParameters()`. Pass only `getClient` to our `mppx` 0.13.5 client: `resolveAccount` comes from the provider's bundled 0.9.3 and its info shape isn't guaranteed to match. |
| 1b | **Global `fetch` is already patched** | **new, must fix** *(source)* | The Accounts SDK provider's `mpp` option **defaults to on**: when the provider is created it runs its bundled `mppx` 0.9.3 with `polyfill: true` in push mode. Any plain `fetch` that gets a 402 is then paid automatically, without our confirm step. Fix: `tempoWallet({ feePayer: SPONSOR_URL, mpp: false })` in `config.ts`. The connector passes unknown options through to `Provider.create`. |
| 2 | Credential re-check vs. a fresh quote | **differs** *(probed)* | On the retry `mppx` rebuilds the challenge from the handler's arguments and pins `amount`, `currency`, `recipient`, `description`, `externalId`, `chainId`, `splits` and `supportedModes` against the echoed challenge. A retry with a recomputed amount (85 → 90) returns **402 `invalid-challenge`: "credential amount does not match this route's requirements"**. Fix, probed: if `Credential.fromRequest(req)` parses and `Challenge.verify(echoed, { secretKey })` passes, reuse the echoed `amount` (`formatUnits(BigInt(echoed.request.amount), 6)`) and `description`. The request then passes binding and goes on to on-chain verification. Recipient is still pinned to the URL's address, and `mppx` enforces `expires` itself. |
| 3 | Sponsored "pull" from a passkey wallet | **differs** *(source)* | The `mppx` client picks **push** for `json-rpc` accounts by default. Push = `sendCallsSync` → the provider's `wallet_sendCalls`, which applies the provider's own `feePayer` config (our `SPONSOR_URL`) when none is passed. So the **wallet broadcasts a sponsored transfer** and sends the tx hash as the Credential (`payload.type = 'hash'`). The server then waits for the receipt and checks amount, currency, recipient and memo binding. The server needs **no `feePayer`**. Pull would go through the provider's `eth_signTransaction` (it exists and handles `feePayer`), but it isn't needed and hasn't been tried. **Not probed live with a passkey**: the first Pay now in I1/I2 confirms it. |
| 4 | CORS header names | **differs** *(source + probed)* | Response: `WWW-Authenticate` (402) and `Payment-Receipt` (200), as expected. Request: `Authorization` **and `Accept-Payment`**. With `polyfill: false` the client's `acceptPaymentPolicy` defaults to `'always'`, so it sends `Accept-Payment` cross-origin too. `mppx` also defines `Payment-Authorization`, which the tempo charge flow doesn't use. |
| 5 | EIP-1167 clone runtime | **confirmed** *(probed)* | `cast code` on clone `0x19d0…62ab` (old factory) = `0x363d3d373d3d3d363d73` + `f0964e9a…798a` (implementation) + `5af43d82803e903d91602b57fd5bf3`, 45 bytes, exact match. |
| 6 | Bad hash Credential | **new** *(probed)* | A hash Credential for a tx that doesn't exist returns **500 `internal-payment-error`** (receipt not found), not a 402. The frontend should show that as a failed payment. |
| 7 | Replay store | **note** | `tempo.charge()` warns that it uses an in-memory replay store. Fine for one server process (the PoC). |
